# STEG Back Office Implementation Audit

Date: 2026-10-02  
Source of truth: `todo/AGENTS.md`  
Scope: `steg-backend`, `steg-back-office`, and the contracts/configuration that connect them.

## Executive Summary

The Angular back office has a mature shell, shared UI, localized screens, and passing QA evidence, but it is still organized around the earlier HR/Finance/Director workflow. The backend already has IAM users/roles, applications, internships, assignments, documents, certificates, finance, notifications, audit, and AI bounded contexts, but the approval and supervision model is not yet the required Admin-as-supervisor model. In particular, current assignment and application schemas reference `employees`, while the authoritative requirement says supervision must reference IAM `users` and allow the single `ADMIN` user to supervise candidates.

The current QA report is evidence for the existing client quality gate, not proof of the AGENTS.md acceptance scenarios. The shared backend supervision scope, atomic approval endpoint, conditional provisioning policy, task review/bulk APIs, and Flutter password-change flow now exist with focused validation. The full AGENTS.md implementation is still incomplete: status migration, supervisor management/reassignment, validation/PDF workflows, AI orchestration, dedicated Angular workspaces, and end-to-end scenarios remain.

## Status Vocabulary

- **OK**: evidence matches the requirement and has focused tests.
- **PARTIAL**: some implementation exists, but the contract, authorization, scope, or acceptance behavior is incomplete.
- **BROKEN**: existing behavior contradicts the requirement or has a known unsafe path.
- **MISSING**: no implementation or no usable end-to-end path found.

## Assumptions and Decisions

1. The required audit belongs in `steg-back-office/docs/` because the back-office project already owns its implementation documentation; the repository root has no `docs/` directory in the current workspace view.
2. The V34 role cleanup is treated as a migration-state concern until verified against a real database. Existing V15 seed content is retained history and must not be edited.
3. Existing `employees` may remain for organization/department concerns, but supervision ownership for the back-office workflow must be represented by IAM `users` so the Admin can supervise without a duplicate identity.
4. Existing finance/certificate/reporting contexts are reusable only where their contracts satisfy the new workflow; their legacy role names and UI assumptions are not authoritative.
5. The first implementation phase is foundation-first: user-backed supervision relation, `SupervisionScopeService`, canonical permissions, and approval tests. Feature screens should follow that contract.
6. **S1 matrix interpretation (2026-10-01):** AGENTS.md §4's sketch `SUBMITTED → MODIFICATION_REQUESTED ↔ RESUBMITTED → APPROVED | REJECTED` is read together with the rule's review actions and Scenario A, so approve / deny / request-modification are allowed directly from `SUBMITTED`; `UNDER_REVIEW` remains an optional two-step review source; `MODIFICATION_REQUESTED` must be resubmitted by the candidate before staff can review again. Every other pair returns 409 `INVALID_STATE_TRANSITION` (candidate submit/resubmit were aligned from 422 to 409 for the same reason). Removed legacy behaviors and the updated legacy tests are listed in `steg-back-office/docs/legacy-removal.md`.
7. **Internship lifecycle trigger (S1):** the §4 chain is now a first-class Admin-only command (`POST /api/internships/{id}/status-transitions`); the real triggers (mobile report submission, manual validation, receipt PDF) will call the same service in S7 so no client can bypass the matrix.
8. **Credentials Resend (S2):** the dialog's Resend reuses the §5.4 mobile-account reset endpoint (`POST /api/intern-accounts/{id}/reset-password`) by resolving the account through `GET /api/intern-accounts?search=email`. The backend generates and emails the new one-time password; the old one is never retrievable. S4 wired the intern-accounts workspace and kept this bare list route untouched for the resend flow; the new paged `/manage` route is additive.
9. **Persistence rule (2026-10-02):** audit rows whose behavior depends on persistence (queries, joins, unique indexes, flush order, transactions, DB-side scoping) may only flip to OK with a Testcontainers integration test against real Postgres; mocked unit tests are complements. The rows re-graded in this pass are §1 (single-identity Admin, Admin capability, supervisor candidate scope, Admin global visibility, selectable directory, 404 leak), §3 (supervisor candidate scope), §4 (mobile account CRUD/reset/activate) and §6 (reassignment, delete guard).
10. **S4 intern-accounts search (2026-10-02):** `GET /api/intern-accounts/manage` filters INTERN/SUPERVISOR accounts server-side; the full-name search uses `LEFT JOIN Candidate c ON c.user = u` with `LOWER(CONCAT(...))` so student names match while candidate-less supervisor accounts are never dropped. The role filter accepts only INTERN/SUPERVISOR (409/422 otherwise); the UI maps "student" to the INTERN role code.
11. **S5 candidate "validation status" (2026-10-02):** the list's validation filter reports whether the candidate owns a usable front-office login, derived from the linked `User` (`CandidateAccountFilter.ACTIVE`/`DISABLED` = the account is enabled and not locked). It is deliberately NOT the application workflow status: validation of a candidate's documents is the `UNDER_VALIDATION → VALIDATED` internship transition, handled in S7. The filter exists because a disabled/locked account is the failure staff hit first in the queue.
12. **S5 candidate soft delete (2026-10-02):** `V41` adds `candidates.deleted_at` and a partial index `idx_candidates_live_created_at`. A deleted profile KEEPS its row so existing history keeps its foreign keys, but it disappears from every staff list and detail. `DELETE /api/candidates/{id}` returns 409 `CANDIDATE_HAS_DEPENDENCIES` while the candidate has applications or internships (tasks and receipts hang off those) and audits `CANDIDATE_SOFT_DELETED`. Hard delete stays out of scope: no screen needs it and it would break the audit trail. **The identity-uniqueness part of this assumption is SUPERSEDED by #13** (the CIN is no longer reserved by a deleted row).
13. **Soft delete releases BOTH identity anchors (pre-check (c), 2026-10-02):** a soft delete sets `deleted_at` AND `user_id = NULL`, and `V42` replaces the V4 `UNIQUE` on `national_id_hash` with the partial index `idx_candidates_live_national_id_hash … WHERE deleted_at IS NULL`. Rationale: a CIN is a permanent national identity number — the same person always presents the same CIN — so reserving it on a deleted row locks out the legitimate owner forever while reserving it for nobody, and `candidates.user_id UNIQUE` kept the account reserved so a second `POST /api/candidates` from the same account died on the DB constraint (409) while the service comment promised the opposite. Invariants kept: two LIVE profiles can never share a CIN (partial unique index) and never share an account (`user_id UNIQUE`, Postgres allowing many NULLs). Proven against Postgres by `CandidateSelfServiceLifecycleIntegrationTest` (`sameCinCanBeRegisteredAgainAfterSoftDelete`, `softDeletedLoginReachesNoData`, `sameEmailCanRegisterAgain`, `softDeletedProfileIsInvisibleToStaff`); the pre-check test found the 409 and the fix is logged in `docs/legacy-removal.md` #14.
14. **The CIN-on-create rule is SELF-SERVICE only (pre-check (a), 2026-10-02):** `POST /api/candidates` is the front-office onboarding endpoint (`@authz.hasRole('CANDIDATE')`), so requiring a CIN there is consistent with the front-office form, which already refuses to submit without one (`ProfileCreateForm.validate`). There is deliberately no staff create endpoint, so the rule is unreachable by any Admin/Supervisor client. Consequence recorded honestly: AGENTS.md §5.1's staff "create" action is not implemented (§3 row re-graded to PARTIAL). A staff create needs a supervision-link decision first (A4 links a created candidate to its supervisor, but supervision today derives from internships), which is why it is not improvised here.
15. **S1b legacy value -> explicit status mapping (2026-10-02, recorded BEFORE coding as required).** Every legacy value, what it meant in the old engine, and the explicit §4 state it maps to. `V39` had already migrated the two application values; `V43` re-asserts them idempotently and migrates the three internship values for the first time.

16. **S6a claim of a staff-created candidate (2026-10-02).** AGENTS.md §5.1 asks staff to CREATE candidates, but §4 has the person register on the front office — so the same human exists twice in the plan. Decision: staff creation writes a profile with **no account**, and the person **claims** it when they register. Rule implemented in `CandidateService.findClaimableProfile`/`claimProfile`:
    * a registration **claims** a LIVE profile that has **no linked account** when the submitted **CIN matches** OR the **email matches** (case-insensitive) — the two things a person always presents the same way;
    * on claim, the account is attached and the **contact** fields the person typed are refreshed, while the **identity/academic/governance** fields (CIN when it matched, university, speciality, diploma, skills, languages, `managed_by`) keep the staff-entered values — staff data must not be rewritable from a public registration form;
    * when the match was by EMAIL and the applicant presents a **different** CIN, the CIN is **adopted** (after the live-uniqueness check): keeping the staff-typed CIN would leave somebody else's CIN on this person's profile, and refusing would lock the rightful owner out of their own profile;
    * a profile that **already belongs to an account is never claimable**: the registration falls through to `CANDIDATE_NATIONAL_ID_DUPLICATE`. Two people are never merged, and the second account gets no profile;
    * a **soft-deleted** staff profile is a tombstone and is never resurrected: the person registers into a **new** row (V42 + V44);
    * the anonymous intake (`AnonymousApplicationService`) claims the same way when it resolves a CIN that belongs to an unclaimed staff profile, so intake never creates a duplicate either.
    Audit actions written: `CANDIDATE_CREATED_BY_STAFF`, `CANDIDATE_CLAIMED` (never with a CIN value), `CANDIDATE_CIN_ACCESSED` (`staff-on-create` for Admin only — a Supervisor's create response stays redacted, exactly like his edits).

17. **Certificate requires VALIDATED, not merely approved (S7 pre-check (c), 2026-10-02).** AGENTS.md §5.7 says "only approved candidates can receive a certificate", but the code gates on internship status `VALIDATED` — deliberately stricter, and sensible: §5.11 requires the Admin's manual validation of report + journal before any receipt/certificate, so a certificate must never be issuable for an internship whose documents were never validated. An approved-but-not-validated internship gets **409 `INTERNSHIP_NOT_VALIDATED`** (a state conflict, not a 422 validation error); a VALIDATED one generates the PDF (201). Proven by `StateMachineRejectionTest.certificateRequiresApprovedValidation` (IN_PROGRESS → 409, then fixture-driven VALIDATED → 201) and the certificate guard in `FinanceCertificateIntegrationTest` (active internship → 409). The flow stays reachable because S7's manual per-document decision endpoint is the (only) producer of VALIDATED via `InternshipLifecycleService`.

18. **S7 validation document resolution + rejection path (2026-10-02).** The intern sends report (+ journal) as deliverables through the existing mobile deliverables channel (A8 — no contract change): the REPORT is the oldest submitted deliverable, the JOURNAL the newest submitted one other than the report, so a resubmitted journal after a REJECTED decision becomes the journal document without swapping the report. A lone deliverable leaves the journal pending (decisions/AI on it are 409/404 until submitted). A REJECTED manual decision returns UNDER_VALIDATION → REPORT_SUBMITTED (new explicit lifecycle edge, Admin-only like every validation step) so the intern resubmits and the next round decides anew; history rows are immutable, current = latest per document. Task-done for the 75% journal input (A2) is one shared function (`TaskCompletionPolicy`: done = APPROVED, denominator excludes CANCELLED; hard-deleted rows absent by construction), used for the python-ai input and shown in the detail. Receipt amounts come from the existing `PaymentCalculationService` with the finance config (A7's fallback was not needed — the source exists), issued WITHOUT the finance-case approval flow and its certificate precondition (receipt precedes the certificate in Scenario A).

37. **Session revocation = state re-check + credential version (2026-10-05).**
     AGENTS.md §10 asks that an access token stop working on deactivation,
     deletion or password reset. Deactivate/delete are covered by re-reading the
     account state on EVERY request in `JwtAuthenticationFilter` (a stateless
     JWT cannot be "revoked", so liveness is bound to the row); a password reset
     is covered by the new V53 `credentials_updated_at` credential version,
     because there the account stays ACTIVE and only the credential changed.
     Refresh (`AuthService.refresh`) and the WebSocket handshake
     (`JwtHandshakeInterceptor`) check the same state. Deliberately NOT
     changed: a user changing their OWN password does not bump the credential
     version — the client holds the token it just used and is expected to log in
     again; bumping it would break the forced first-login rotation in all three
     clients. Pinned by `SessionRevocationIntegrationTest` (3, Testcontainers +
     real HTTP), each case starting from a FULLY usable session: the forced
     rotation is completed first, otherwise the filter answers 403
     `PASSWORD_CHANGE_REQUIRED` and the 401 could not be observed.
